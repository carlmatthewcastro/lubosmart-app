# Account creation implementation plan

Audit date: 2026-10-13 (Asia/Manila). **Proposal only; no application change is approved or performed.** The workbook was found under `documentation/standards/`, not the requested `docs/standards/`. See [audit](ACCOUNT_CREATION_AUDIT.md) for conflicts and [all 150 cases](ACCOUNT_CREATION_TRACEABILITY.md) for exact requirements and source evidence. Assumptions A1–A16 are proposed rules, not automatically authoritative system requirements.

## Preconditions and preservation rules

Approve the lifecycle and field decisions before implementation. Preserve existing verified accounts, approvals, rejection reasons, documents, stores, center membership, orders, parcel/COD history, Google sign-in, password recovery and profile re-review. Do not rewrite historical migrations, drop enums/tables, remove old documents, reset passwords, silently approve Buyers, or disable public Courier registration during this audit. New indexes require an inventory of existing duplicates and an approved resolution policy; never delete records to make an index succeed.

Do not build a second independent authentication stack or integrate the saved API branch as part of this account audit. Use current Laravel controllers/Form Requests/policies/services and the shared React registration component. Keep canonical `courier`/`sorting_center` role values unless a separate migration is approved. No production migration, testing, deployment, or real-recipient email is proposed without explicit authorization.

## Phase 0 — Reconcile the acceptance contract

**Dependency:** first. **Cases addressed:** every one of the 150 IDs; specifically A1–A16 and the conflicts identified in the matrix. **Changes:** approve an assumption-by-assumption decision record and corrected execution fixtures, not application behavior.

- Choose credentials-only staged onboarding versus workbook full-form signup. Under the latter, validate all mandatory fields/documents before creating any account, as required by the workbook's rejection outcomes. Under the former, update the acceptance contract explicitly; do not claim the unchanged workbook passes.
- Decide Buyer approval versus activation after verification; registration link versus five-minute OTP; public Courier signup versus Logistics-created invitation. Retaining a current feature and adding an alternative is not compliant with a case explicitly prohibiting it unless the workbook is reconciled.
- Resolve company-versus-center ownership, Google verified-email behavior, uniqueness normalization, adulthood/timezone, A15's ten-versus-eleven digit inconsistency, Seller Corporation/DTI rejection fixture mismatch, and date-formula recalculation.

**Existing code involved:** `RegisteredUserController::store`, `GoogleAuthController::callback`, `EmailVerificationLinks`, `User::onboardingRoute/canOperate`, `SubmitApplicationRequest`, `ApplicationController`, `ApplicationReviewController`, company/center policies and existing contrary tests. **Files likely to change:** decision/acceptance records only if separately requested; no application files in this phase. **Migrations:** none. **Security:** avoid accidental weakening of approval and ownership boundaries. **Tests:** review expected contracts; do not relabel existing tests as workbook passes. **Regression risk:** implementing guessed assumptions would invalidate working accounts and approval workflows. **Exit:** user has chosen each material conflict and accepted fixture corrections.

## Phase 4 — Implement the chosen email verification lifecycle

**Dependencies:** Phases 0–3 for full-form registration. **Cases addressed:** TC-BUY-001,023–028; TC-SEL-001,032–037; TC-LOG-001,032–037. A9 must be decided first.

**Proposed change:** if A9 is accepted, add a dedicated six-digit registration OTP purpose with five-minute expiry, normalized current-email binding, hashed storage, limited attempts/requests, lock-based single use and replacement on resend. Reuse existing security service principles, not password-purpose records. Route successful verification through the approved Buyer/Seller/Logistics lifecycle in Phase 5. Preserve recovery/profile ten-minute flows and explicit Google verified-email handling. If verification links remain, reconcile those workbook cases rather than falsely reporting OTP compliance. If both methods coexist, decide legacy link expiry/retirement and prevent unintended verification/approval bypass.

**Existing code involved:** `EmailVerificationLinks::send/verify`, `EmailSecurityCodes::send/verify/consume`, User notification method, verification controllers, Registered event, Google callback. **Files likely to change:** `routes/auth.php`, service/notification classes, `User`, registration notice and OTP page/components; verification/recovery tests. **Migrations:** possibly dedicated registration code record or approved additional purpose metadata/attempts; retain old link records until approved transition. **Security:** five-minute codes need brute-force limits, atomic consumption, no raw code in persistent queues, no account/session switching, current email invalidation, delivery failure recovery and resend cooldown. Controls are engineering safeguards for the proposed OTP, not additional invented business requirements.

**Automated tests:** correct/incorrect/blank/5/6/7-digit/letters, exact 5:00 and 5:01 boundary (inclusive rule decided), old/new resend codes, exhausted attempts, concurrent verification/resend, mail transport failure, changed email, purpose isolation, pending-state restrictions and OAuth.
