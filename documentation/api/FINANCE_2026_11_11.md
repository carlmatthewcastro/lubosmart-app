## Current return/refund contract

> [!IMPORTANT]
> New requests use workflow version 3. Admin approval credits coins and records liability without Buyer acceptance, Seller receipt or reserve-funding gates. Legacy offer and custody behavior must not override this contract.

- Existing return URLs remain. Buyer POST accepts original seller_order_id, reason/reason_kind, items [{order_item_id, quantity, amount}], shipping_amount and optional evidence images. Item amount and shipping_amount are PHP decimal values. Legacy whole-parcel clients can omit items; the server derives remaining eligible quantities.
- Web Admin PATCH action approve requires items with approved quantities/amounts, shipping_amount, responsibility (seller/logistics/buyer/platform), separate return_shipping_responsibility, physical_return_required, and reason. For no-return decisions, shipping responsibility is not_required. Successful approval credits spendable coins and records liability atomically. No client-generated financial reference is required.
- Legacy offer creation returns a validation message directing users to combined approval. Buyer accept-offer is an ownership-checked informational no-op; it neither gates nor issues credit.
- GET return projections add refund_status, task (including independent status/proof metadata), settlement_state, requested/approved item amounts/quantities and scoped wallet/payment context. Original parcel projection and server-computed allowed_actions remain. The compatibility status field is not authoritative for physical custody; clients must use task.status.
- Task actions are assign, collect, facility_receive, assign_seller, accept_seller_dispatch, deliver_seller, receive and discrepancy. Collection and Seller delivery require proof image and recipient_name. Empty optional proof is accepted on other supported actions; supplied images must be valid JPG/PNG, at most 5 MB. No Seller tracking/scanner value is required. Receive requires recorded Seller delivery and condition/restock decision.
- Multipart web mutations use POST plus \_method=patch. Native PATCH actions share validation, ownership, Rider assignment and operational-center checks. Native private proof URLs are GET /api/v1/returns/{return}/proof/{proof} and GET /api/v1/logistics/returns/{return}/proof/{proof}.
- Logistics may record_return_fee from the linked case with leg (return_collection/return), amount and reason; task, original delivery and assigned Rider are resolved server-side. This records a fee/transport obligation, not a wallet change or cash transfer. Existing rider-payments also accepts return_task_id; repeated case fees cannot alias different return tasks on the same parcel.
- API validation remains 422 with errors; conflicts remain 409; authorization remains role/ownership scoped. Inertia.js state conflicts are surfaced as recoverable form errors. Neither assignment, receipt nor discrepancy can issue another credit.

## Cash, wallet and resource additions

Existing endpoints and decimal merchandise/shipping fields remain compatible. Current [cash/coin rules](../WORKFLOWS.md#finance) separate commercial value, cash funding, wallet liability and custody. Mobile UI work is paused; backend availability does not establish a corresponding native screen.

| Interface                                        | Additive behavior                                                                                                                                                    |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User resource                                    | Riders receive `rider_capability`: pickup, delivery, or both                                                                                                         |
| Delivery resource                                | Separate pickup/delivery IDs, custody type/rider, capability-aware `allowed_actions`; legacy `rider_id` remains current assignment                                   |
| Parcel resource                                  | `cod_total` is the **remaining cash due**, formatted as a decimal string; `cod_due_cents`, `coins_redeemed_cents`, and `merchandise_cash_cents` are integer centavos |
| `POST /api/v1/orders`                            | Optional integer `coins_to_redeem_cents`, default 0; existing checkout UUID idempotency, reviewed prices, shipping and voucher validation remain                     |
| `GET /api/v1/wallet`                             | Owning Buyer balance and paginated signed ledger; no caller-selected Buyer ID                                                                                        |
| `POST /api/v1/returns/{return}/accept-offer`     | Ownership-checked informational no-op; approval already credits coins, so no consent or credit is issued here                                                        |
| `GET /api/v1/shop-vouchers?store_id=...`         | Public, active, nonexpired, nonexhausted vouchers for an operational shop; reading consumes no usage                                                                 |
| `GET/PATCH /api/v1/logistics/returns[/{return}]` | Operational Logistics token; own-center reverse queue and existing authorized reverse actions                                                                        |
| Existing return/earnings resources               | Reverse leg IDs/timestamps/actions, authorized refund breakdown/offer, and own weekly compensation history                                                           |
| Finance                                          | Order-date/reference/COD-status filters, scoped transaction references and cash/coin breakdowns; Admin still cannot manage/read Logistics wages                      |

Historical version-2 returns use facility receipt and Seller-return handover. Actions are `assign`, `collect`, `facility_receive`, `assign_seller`, `accept_seller_dispatch`, then Seller `receive`. Collection requires delivery capability; facility-to-Seller transport requires pickup capability. The original tracking reference is retained. Version-1 in-progress returns keep their historical receipt path. New requests use the version-3 task actions above, including Seller-delivery proof.

Forward QR actions remain `picked_up`, `receive`, and `accept_dispatch`. POD completion has a required recipient name, photo, supported note, optional remarks, and COD confirmation when cash is due. Exceptional replacement uses `exception_assign` after facility receipt and a separately scanned `accept_transfer`; it does not repeat a forward checkpoint. Native callers should render server-provided actions and never infer permission from a status alone.

Clients must not calculate COD as subtotal + shipping when a parcel has coins. Merchandise subtotal and commission remain based on net sales; coins are a payment source. Existing native checkout omits coins and therefore keeps ordinary COD behavior. Existing rider/parcel screens already display the server's `cod_total`. New wallet/template/mobile screens remain future mobile work; these backend contracts are available now.

Buyer contact access follows the actual task. Pickup/seller-return history does not grant delivery contacts or proof access. Buyer refund/wallet figures remain hidden from Logistics/Rider reverse resources, and public voucher discovery never reveals Buyer usage identities.

## Finance reads and platform receipt

Laravel remains authoritative. Both endpoints require an unexpired Laravel Sanctum bearer token with `api:v1` and `role:<current role>`, and an operational account. Responses are private/no-store. Monetary overview values are integer PHP centavos; clients format them without recalculating allocations.

| Endpoint                                   | Access                          | Response                                                                                          |
| ------------------------------------------ | ------------------------------- | ------------------------------------------------------------------------------------------------- |
| `GET /api/v1/finance`                      | Admin, Seller, Logistics, Rider | `data.role`, `data.amounts` (label → integer centavos), `data.discrepancies`, `data.legacy_rates` |
| `GET /api/v1/logistics/settlements?page=1` | Logistics                       | `data.entries` paginator, `data.totals`, `data.cash_model`, `data.can_record`                     |

Overview authorization is server-side: Seller sees own store, Logistics own operational centers, Rider own COD/compensation. Admin cannot read private Rider wage totals. Buyers continue using owned purchase/return endpoints. Unknown/foreign company filters cannot broaden scope.

Shipping entries contain parcel/provider identity, tracking, original allocation in centavos, expected product remittance, recorded receipt/reference/date if present, new shipping refund component if known and the existing COD reconciliation concept. Historical unknown refund splits are `null`, not invented zeros. `cash_model` is `logistics_retains_shipping`. Logistics settlement reads return `can_record: false`; actual platform remittance receipt is recorded through the authorized web action below.

Admin confirms actual full net-product cash receipt through the authenticated web `POST /logistics-settlements/{parcel}` action with `amount` (PHP, at most two decimals), unique `reference`, actual `received_on` (`YYYY-MM-DD`, no future date) and evidence `notes`. Shipping stays with Logistics. That action uses a transaction and audit record; no transfer is initiated. The platform receipt is a new Seller payout prerequisite.

Ordinary Seller `ParcelResource.recipient` now includes only name, city and province. Phone, street, barangay, region and ZIP remain available from the authorized own-parcel `GET /api/v1/seller/orders/{sellerOrder}/waybill` endpoint. Clients must not rely on ordinary list responses for contact/address labels. Flutter printing already fetches that endpoint.

Return read responses now include reviewed `responsibility` and `responsibility_reason`. No Buyer/Seller/Rider token can establish liability or record an Admin refund. Native Finance overview is reachable from Account for Seller/Rider; Admin/Logistics continue the existing website-only native navigation scope.
