## Migration considerations

Four migrations add normalized account identifiers and email verification codes,
seller/application fields, logistics/rider invitations, and product wishlists.
Legacy duplicate normalized emails, valid phone numbers, store/company names or
rider plates can stop the migrations. Reconcile these records deliberately; do
not delete customer records or disable uniqueness checks to force deployment.
Some migrations are not reversible. Keep verified database and private-upload
backups outside the Docker volumes and off the VM before migrating.

## Azure release procedure

Use the established SSH identity and checkout. First inspect the deployed revision,
working-tree changes, Compose services, available disk space and backup status.
Never overwrite production `.env`, regenerate `APP_KEY`, seed demo accounts, run
`migrate:fresh`, or remove Docker volumes.

After review, deploy the approved immutable commit using the existing manual
[deployment procedure](README.md#release-steps). That procedure uses `main` only
after an explicitly authorized merge. A branch push does not authorize merging
into `main`; an approved feature-branch deployment must pin its reviewed commit.
Retain the previous image and revision for recovery. Build successfully before
entering maintenance, stop the queue while migrating, clear cached configuration
and views, apply migrations, recreate the queue and restore service.

Verify `/up`, homepage, sign-in, registration, real email verification, queue logs,
uploads, role boundaries and cart access. Record the deployed commit and check
that the frontend is served from the new `public/build` manifest. SSH access,
production credentials and backup verification are required before executing the
deployment; this handoff does not claim they have been checked.
